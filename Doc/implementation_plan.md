# 구현 계획서 - 비디오 속도 조절 기능 (0.1x ~ 6.0x)

이 계획서는 웹 기반 비디오 에디터의 메인 비디오 트랙(Video Track 1) 및 PIP 오버레이 트랙(Video Track 2) 클립의 재생 속도를 0.1배속부터 6.0배속까지 개별 조절할 수 있도록 하는 기능에 대한 명세입니다. 속도 변경 시 타임라인 상의 클립 길이가 유기적으로 변경되며, 브라우저 실시간 프리뷰 및 로컬 FFmpeg 렌더링 명령어에도 정상적으로 속도가 반영되도록 구현합니다.

## 사용자 검토 필요 사항

> [!IMPORTANT]
> **주요 설계 의사결정 사항:**
> 1. **기본 배속 및 범위**: 모든 비디오 클립은 기본적으로 `1.0x` 배속을 가집니다. 속도 조절 범위는 슬라이더 기준으로 `0.1x`부터 `6.0x`까지이며 `0.1x` 단위로 세밀하게 조절할 수 있습니다. 추가로 자주 쓰이는 배속(`0.5x`, `1.0x`, `2.0x`, `4.0x`)을 빠르게 지정할 수 있는 프리셋 버튼을 제공합니다.
> 2. **타임라인 클립 길이의 동적 연동**: 배속이 변경되면 사용자가 지정했던 원본 영상의 컷 구간(`sourceStart`, `sourceEnd`)은 유지된 채로 타임라인 길이($D_{timeline}$)가 다음과 같이 자동으로 변경됩니다: $D_{timeline} = (sourceEnd - sourceStart) / speed$.
> 3. **트리밍 핸들 조작 시 배속 적용**: 타임라인에서 클립의 왼쪽/오른쪽 트리밍 핸들을 드래그할 때 마우스 이동 거리(시간)에 클립의 속도 배율을 곱하여 원본 영상 구간의 타임스탬프를 올바르게 계산합니다.
> 4. **FFmpeg 명령어 생성 (오디오 멀티-템포 체이닝)**:
>    - 비디오: `setpts=PTS/speed` 필터를 적용합니다.
>    - 오디오: FFmpeg의 `atempo` 필터는 `0.5` 이상 `2.0` 이하만 지원합니다. 따라서 배속이 이 범위를 벗어나는 경우(예: `6.0x`), 다중 `atempo` 필터를 자동으로 체이닝하여 구현합니다 (예: `6.0x` -> `atempo=2.0,atempo=2.0,atempo=1.5`).

# 구현 계획서 - 애니메이션 WebP 내보내기 (목표 용량 보장)

SNS 업로드용 **움직이는 WebP**를 내보내는 기능입니다. 요구사항은 5초 이내 · 20fps · 스마트폰에서 보기 좋은 용량(2~7MB, 기본 3MB)이며, **결과물이 목표 용량을 넘지 않도록 보장**하는 것이 핵심입니다.

## 사용자 검토 필요 사항

> [!IMPORTANT]
> **주요 설계 의사결정 사항:**
> 1. **품질 80% 고정을 쓰지 않음**: 최초 요구는 "80% 품질"이었으나, 실측 결과 q80은 720×1280에서 2,115KB(배경이 단순한 릴스)~4,053KB(에펠탑 격자 배경)로 목표를 넘나듭니다. 같은 조건에서 콘텐츠에 따라 결과가 최대 2배까지 차이 나므로 **q80은 고정값이 아니라 탐색이 도달할 수 있는 한 점**으로 취급하고, 목표 용량을 상한으로 두고 품질을 최대화합니다(단순 콘텐츠는 q=84까지, 복잡 콘텐츠는 q=54까지 내려감). 품질 하한은 `q=55`.
> 2. **구간은 타임라인에서 직접 지정**: 최대 5초. 2초·3초도 가능하며 길이가 가변입니다. **프레임 수가 곧 용량 예산**이라 구간이 짧을수록 같은 용량에서 화질이 올라갑니다(실측: 2.6초 구간은 1080×1920을 그대로 유지, 5초 구간은 720×1280으로 하향).
> 3. **해상도 하향은 사용자 확인 후 진행**: 목표 달성을 위해 해상도를 낮춰야 하면 임의로 낮추지 않고 확인을 받습니다. 3지 선택(낮춰서 진행 / 현재 화질로 저장 / 취소).
> 4. **20fps 권장**: WebP 애니메이션의 프레임 duration은 ms 단위라 20fps = 정확히 50ms로 드리프트가 없습니다. 30fps는 33.33ms 반올림으로 어긋납니다.

## 변경 제안 사항

### [NEW] `webp-exporter.js`
- **무손실 중간본 1회 생성**: 기존 `filter_complex`를 그대로 재사용해 프로젝트 해상도로 합성한 뒤, 출력 단계 시킹(`-ss`/`-t`)으로 구간만 잘라 `libx264 -qp 0` 중간본을 만듭니다. 모든 프로브가 이 파일을 재사용하므로 필터 그래프는 한 번만 돕니다.
- **프레임 솎아내기 탐색**: `libwebp_anim`은 프레임 간 예측을 하지 않아 각 프레임이 독립적으로 인코딩됩니다(`-cr_threshold`가 무효였던 이유). 따라서 N분의 1 프레임만 인코딩하면 크기가 정확히 N분의 1이 되고, 전체 크기를 N배로 예측할 수 있습니다. 실측 **오차 +1.0%, 속도 3.5배**(13.9초 → 4.0초). 프레임이 60개 미만이면 1/2, 30개 미만이면 솎아내지 않습니다.
- **병렬 이진 탐색**: `libwebp_anim`은 단일 스레드라 프로세스 병렬화가 유일한 단축 수단입니다. 라운드당 3개를 동시 실행해 `q ∈ [55, 95]`를 좁힙니다.
- **해상도 하향 추정**: WebP 크기는 화소수에 선형이 아니라 **거듭제곱(지수 0.6)** 으로 비례합니다(실측 0.59 / 0.64). 선형으로 가정하면 필요 해상도를 너무 크게 잡아 확인을 여러 번 받게 됩니다.
- **확정 인코딩**: 솎아낸 프레임은 결과물로 쓸 수 없으므로 전체 프레임으로 다시 인코딩합니다. 실제 크기가 목표를 넘으면 국소 기울기로 품질을 낮춰 재시도(최대 3회)합니다.

> **ffprobe로 애니메이션 WebP를 검증할 수 없습니다.** `ffprobe`는 `image data not found`로 실패하고 width/height도 0으로 나옵니다. 파일은 정상이며 ffprobe의 한계입니다. RIFF/VP8X/ANIM/ANMF 청크를 직접 파싱해 확인하세요.

### 수동 기능 테스트
1. 릴스를 타임라인에 추가 → 구간 밴드가 보이고, 핸들 드래그가 5초에서 멈추는지.
2. `WebP 내보내기` → 설정 모달에서 구간·용량·fps 확인 후 실행.
3. 배경이 복잡한 릴스(에펠탑 등)로 3MB 목표 → 해상도 하향 확인 창의 3개 버튼 각각 동작.
4. 결과 이미지가 브라우저에서 **애니메이션으로 재생**되는지, 다운로드·저장 폴더 열기 동작.
5. 프로젝트 저장 → 새로고침 → 복원 시 슬라이더·fps·구간 유지.
